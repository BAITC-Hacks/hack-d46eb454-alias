# HACKALEM AI — задание для ИИ-агентов

## Цель

За 5 часов собрать работающий MVP расчёта заказов поставщикам для ТОО «Электрокомплект». Первый охват — склад Алматы и ассортимент ИЭК. Менеджер загружает Excel → получает объяснимые рекомендации → корректирует → утверждает → экспортирует заказ.

Приоритет: корректность расчёта и пять обязательных требований заказчика, затем удобство интерфейса. Локальный запуск обязателен; деплой — при наличии времени и разрешения на размещение данных.

## Архитектура и разделение работы

- **Сервер:** Python + FastAPI; импорт, проверка данных, прогноз, расчёт и экспорт.
- **Интерфейс:** React; три экрана: данные и настройки, рекомендации с карточкой товара, утверждение заказа.
- **Хранилище:** SQLite; исходные записи, параметры и версии расчётов, рекомендации, ручные изменения и статус утверждения.
- **Поток:** Excel → нормализация → очистка спроса → компенсация stockout → сезонность и тренд → расчёт заказа → проверка менеджером → экспорт.
- **Агент сервера:** импорт, алгоритмы, API, проверки расчёта. **Агент интерфейса:** экраны и интеграция. До параллельной реализации зафиксировать общий контракт API и пример ответа; работать в отдельных ветках, не менять чужую область без согласования.

Расчёт: `max(0, прогноз спроса на срок поставки и период до следующего пересмотра + страховой запас − доступный остаток − учитываемые поступления)`. Поступления учитывать по ожидаемым датам; отдельно показывать дефицит до их прибытия. Затем применять минимальную партию и подтверждённую кратность. Объяснения строить из компонентов расчёта, без зависимости от внешней языковой модели.

## Данные и ограничения

- В архиве IEK.zip: детализация продаж преимущественно за 2025–2026 годы, месячные продажи и начальные остатки за 2024–2026 годы, товары в пути с датами, MOQ и таблица сезонности. Детализация — по Алматы, до 22.09.2026. Файлы каждому участнику доступны локально; абсолютные пути не зашивать в код.
- Нет подтверждённых текущих остатков, точных интервалов stockout и ID клиентов. Месячный начальный остаток не считать текущим; пустую ячейку не приравнивать автоматически к нулю; отсутствие продаж не считать доказанным stockout.
- Поддержать загрузку текущих остатков, интервалов stockout и обезличенного `customer_id`. Недостающие сведения проверять на отдельно обозначенных синтетических сценариях. Не выдавать сценарные результаты за подтверждённый заказ по реальным данным.
- Категории, сроки поставки и плановый прирост задавать через явные настройки/загрузку; отмечать источник и допущения. Категории должны влиять на прогноз или политику запаса. Исторический тренд и плановый прирост не учитывать дважды.
- Проверять дубли кодов, типы документов, отрицательные количества и единицы измерения. Продажи в метрах и закупки бухтами требуют явного коэффициента пересчёта. MOQ не считать кратностью без подтверждения.
- Детальные и месячные продажи использовать для сверки/дополнения истории, не складывать за один период. Неполный сентябрь не сравнивать напрямую с полными месяцами. При тестировании прогноза не использовать будущие данные, включая готовые коэффициенты сезонности.
- Разовые продажи выявлять по размеру и повторяемости; при наличии ID — также по клиенту. Номер документа не заменяет ID клиента. Сохранять исходные операции и возможность отменить исключение.
- Данные обрабатывать локально, не добавлять архивы, выгрузки и рабочую базу в Git, не отправлять внешним сервисам без разрешения. Не использовать неанонимизированные сведения о клиентах.
- Не отправлять заказ поставщику автоматически. Утверждение выполняет сотрудник. Экспорт CSV/XLSX не объявлять совместимым с 1С до проверки образца требуемого формата.
- За рамками MVP: перемещения между складами, выбор оптимального поставщика, полноценная интеграция с 1С, чат с ИИ и сложная система ролей.

## Критерии готовности

- [ ] **Базовая потребность:** импорт реальных файлов, отчёт об ошибках и расчёт по артикулам. Продажи, остатки, поставки в пути, категории и плановый прирост действительно используются; отдельные тесты показывают ожидаемое влияние каждого источника там, где не мешают нулевой заказ или округление.
- [ ] **Сезонность и рост:** прогноз воспроизводит заданный сезонный паттерн и устойчивый тренд. Проверено на контролируемых сценариях; выполнено сравнение с простым средним на отложенном периоде реальной истории без утечки будущего.
- [ ] **Упущенный спрос:** подтверждённый stockout повышает оценку спроса относительно расчёта по сырым продажам. Оценки и предположения явно обозначены.
- [ ] **Разовые заказы:** искусственно добавленная крупная разовая продажа, включая сценарий одного клиента, выявляется и исключается из регулярного спроса; регулярный прогноз до/после совпадает в пределах численной погрешности. Повторяющиеся крупные продажи не исключаются только из-за размера.
- [ ] **Результат:** рекомендации сгруппированы по поставщикам; у каждой строки есть количество, срочность и объяснение компонентов расчёта. Несколько поставщиков проверены на синтетическом наборе.
- [ ] **Рабочий сценарий:** загрузка → расчёт → изменение количества с сохранением причины → утверждение → экспорт проходит целиком. Изменение утверждённого заказа требует повторного утверждения.
- [ ] **Граничные случаи:** проверены пустая история, отсутствующие обязательные данные, нулевой спрос, избыток запаса, поздняя поставка, аномалия, MOQ и пересчёт единиц. Нехватка данных не скрывается за правдоподобным числом.
- [ ] **Передача:** README содержит запуск на другом компьютере, методику, исключение выбросов, ограничения и демонстрационный сценарий. Проверки проходят; локальный MVP запускается по инструкции.

## Порядок работы

План → архитектура и контракт API → реализация → тесты → ревью → документация → проверка запуска. Человек выбирает приоритеты и принимает результат; агенты реализуют и предъявляют доказательства проверок. Ориентир: 30 минут на контракт, 2 часа на параллельную разработку, 1 час на интеграцию, 45 минут на проверки, 45 минут на документацию и демонстрацию.
