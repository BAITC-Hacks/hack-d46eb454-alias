# Интерфейс закупщика

Прочитай корневые `AGENTS.md`, `PROJECT_BRIEF.md` и согласованный контракт API. Интерфейс русскоязычный; расчёт выполняется сервером. До готовности сервера используй синтетические ответы той же схемы и заметную пометку демонстрации.

## Три экрана

1. **Данные и настройки.** Загрузка, дата/охват данных, число принятых и проблемных строк, недостающие поля. Ввод срока поставки, периода пересмотра, категорийных настроек и прироста с единицами и источником. Сценарные остатки нельзя выдавать за выгрузку партнёра.
2. **Рекомендации.** Группировка по поставщику; код, товар, единица, остаток, ожидаемые поступления, количество заказа и срочность. Поиск, фильтры и постраничная выдача/виртуализация при необходимости. Карточка товара показывает продажи, очищенный спрос и прогноз как разные серии, а также компоненты расчёта.
3. **Заказ.** Рассчитанное и ручное количества рядом, причина изменения, статус, утверждение сотрудником и экспорт. После изменения утверждённой версии показывай снятое утверждение и необходимость повторного. Не показывай отправку поставщику, которой нет в MVP.

## Состояния и интеграция

- Обрабатывай загрузку, пустой результат, ошибки формата/сети и недостающие обязательные данные. `null` показывай как «нет данных», ноль — как ноль.
- Для старого результата после изменения параметров показывай необходимость пересчёта. Ответ более раннего запроса не должен затирать новый.
- Не создавай объяснения/цифры на клиенте заново. Дата остатка, допущения, единицы и причина срочности приходят из API.
- Пока нет цен, не показывай вымышленную стоимость или экономию. Фактические и синтетические данные визуально различимы.
- В таблицах используй читаемые подписи, клавиатурную навигацию и статусы с текстом, не только цветом. Приоритет — рабочий экран закупщика на ноутбуке, затем адаптация размеров.

## Проверка

Пройди локально весь путь от загрузки синтетических файлов до скачанного заказа. Проверь ручной ноль, отрицательное/дробное количество с учётом единицы, потерю утверждения, сетевую ошибку и длинные наименования. Свяжи экран с реальным API перед заявлением готовности. Браузерный MCP либо доступный встроенный браузер пригодны для проверки; повторяемый сквозной тест должен жить в проекте. Скриншот не заменяет проверку поведения.
