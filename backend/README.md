# Сервер HACKALEM AI

Backend реализует согласованные маршруты из `contracts/openapi.yaml`. Расчётное ядро находится в `backend/replenishment.py` и не зависит от HTTP, SQLite и Excel. Исходные книги, снимки загрузок и база хранятся только локально в `data/` (каталог исключён из Git).

## Запуск

Из корня репозитория:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r backend/requirements-dev.txt
.venv/bin/python -m uvicorn backend.main:app --host 127.0.0.1 --port 8000
```

Проверки:

```bash
.venv/bin/python -m pytest -q tests/backend
.venv/bin/python -m pytest -v tests/backend/test_fixtures.py::test_agreed_scenario
```

Проверка API: `GET http://127.0.0.1:8000/api/health`. Документация `/docs` показывает согласованный контракт. Для синтетической демонстрации отправьте `POST /api/recommendations/calculate`:

```json
{
  "dataset_id": "synthetic-fixtures",
  "calculation_date": "2026-09-23",
  "warehouse_scope": "Алматы",
  "review_period_days": 7,
  "default_lead_time_days": 21,
  "service_level_z": 1.65
}
```

Ответ содержит шесть артикулов в группах поставщиков. `run_id` из ответа используется для чтения, корректировки, утверждения и экспорта. Менеджер указывает причину и автора при корректировке; после изменения утверждённой версии нужно повторное утверждение. CSV/XLSX выдаётся только для утверждённого заказа. Экспорт не заявлен совместимым с 1С без образца её импортного формата.

## Загрузка Excel

`POST /api/import/preview` принимает несколько `.xlsx` или один `.zip` с книгами и поле `warehouse_scope`. Ответ включает `preview_id`, распознанные файлы, количество нормализованных записей, ошибки/предупреждения и неподдержанные поля. `POST /api/import/commit` с этим `preview_id` создаёт неизменяемый снимок `dataset_id`; повторный расчёт использует его. Проблемные строки сохраняются локально с именем файла, листом и номером строки. Одинаковый файл внутри одной загрузки пропускается.

Архив партнёра даёт детализацию продаж, месячные продажи и начальные остатки, поставки в пути, MOQ и коэффициенты сезонности. Детализация продаж и месячные итоги не суммируются за один период. Связь выполняется только по строковому коду 1С. В текущей детализации положительные строки «Расходная накладная» считаются продажами; отрицательные количества и другие типы документа попадают в отчёт и не превращаются через `abs()` в продажи. Пустые значения не превращаются в ноль. В поставках даты берутся из заголовков, а одинаковые строки документа помечаются как спорные. Для метровых позиций с пометкой о бухтах поступление блокируется до подтверждения перевода единиц. MOQ не считается кратностью упаковки.

Чтобы рассчитать реальные заказы, дополнительно загрузите книгу текущих остатков со столбцами **Код 1С**, **Остаток**, **Дата**, **Склад**. Она должна относиться к выбранному складу. Дополнительные книги могут задавать `Категория` по коду 1С и подтверждённые интервалы `Начало`/`Конец` stockout. Срок поставки и плановый прирост передаются явно в запросе расчёта. Без актуального остатка сервер возвращает предупреждение и блокирует утверждение операционного заказа; месячный остаток «на начало месяца» не подменяет сегодняшнее значение.

## Метод расчёта

Выбросы: медиана и MAD по объёму положительной операции, плюс концентрация у обезличенного клиента, если его ID предоставлен. Повторяющиеся крупные покупки одного клиента сохраняются. Исторический уровень спроса очищается от исключённых операций; коэффициенты сезонности читаются из нормированных значений файла `Сезонность ИЭК.xlsx`, а тренд считается отношением двух последних 28-дневных окон. В реальной истории операции перед прогнозом приводятся к базовому уровню с помощью тех же месячных коэффициентов. Компенсация stockout применяется только к подтверждённым интервалам. Страховой запас равен `z × σ(спрос за срок поставки)`; при отсутствии внешней оценки σ выводится из дневной изменчивости наблюдаемых продаж и масштаба срока поставки.

Горизонт равен сроку поставки плюс интервал пересмотра. Потребность: `max(0, прогноз + страховой запас − доступный остаток − подтверждённые поступления внутри горизонта)`. При положительной потребности применяется MOQ, затем подтверждённая кратность. Поступления после горизонта и просроченные неподтверждённые поставки не уменьшают потребность. Отдельно проверяется дата возможного дефицита до новой поставки. Объяснение строится из чисел компонентов ответа без LLM.

Ограничения текущих данных: в IEK.zip нет актуального остатка с датой, обезличенного ID клиента, подтверждённых интервалов stockout, справочника категорий и сроков поставки. Сезонность в исходной книге рассчитана по агрегированной выручке, поэтому её применимость к количеству конкретного артикула требует проверки. Синтетические fixtures показывают работу методов, но не подтверждают точность прогноза на истории партнёра.
