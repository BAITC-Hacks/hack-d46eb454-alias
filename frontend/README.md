# EKT — интерфейс закупщика

React + TypeScript + Vite интерфейс работает с локальным FastAPI. Согласованный контракт — `../contracts/openapi.yaml`; перевод ответа сервера в модели экранов находится в `src/api/mapper.ts`. Исходные данные партнёра и рабочая база остаются локально вне Git.

## Запуск

Из корня репозитория запустите сервер:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r backend/requirements-dev.txt
.venv/bin/python -m uvicorn backend.main:app --host 127.0.0.1 --port 8000
```

Во втором терминале:

```bash
cd frontend
npm ci
npm run dev
```

Откройте `http://127.0.0.1:5173/#/data`. Прокси Vite направляет `/api` на локальный сервер. При другом адресе сервера используйте `API_PROXY_TARGET` из `.env.example`.

Проверки из `frontend/`:

```bash
npm run build
npm test
npm run test:e2e
```

Playwright запускает FastAPI и Vite при наличии `.venv` в корне. Для проверки настоящего архива дополнительно задайте `IEK_ARCHIVE_PATH=/абсолютный/путь/IEK.zip`; этот файл не копируется в репозиторий. Если Chrome отсутствует, установите Chromium и запустите с `PLAYWRIGHT_CHANNEL=chromium`.

## Рабочий путь

1. На экране «Данные» выберите `.xlsx` или архив `.zip`, задайте склад и нажмите «Проверить файлы». Список источников, количества строк и замечания приходят из `POST /api/import/preview`.
2. Задайте дату расчёта, срок поставки, период пересмотра, коэффициент `z` и плановый прирост. «Сохранить набор и рассчитать» вызывает `POST /api/import/commit`, затем `POST /api/recommendations/calculate` с выданным `dataset_id`.
3. На экране «Закупки» результаты поиска и фильтров берутся из одного ответа `RecommendationRun`; дополнительного опроса сервера и серверной пагинации нет. При перезагрузке приложение запрашивает сохранённый `run_id` через `GET /api/recommendations/runs/{run_id}`.
4. На экране «Заказы» поставщики — разделы одного расчёта. Правка количества с причиной вызывает `PATCH /api/recommendations/runs/{run_id}/items/{item_id}/adjust`. Подтверждение относится ко всему run и вызывает `POST /api/orders/{run_id}/approve`. CSV и XLSX скачиваются с сервера после утверждения.

Кнопка синтетического примера тоже обращается к FastAPI с `dataset_id=synthetic-fixtures`; это не старые локальные `fixtures/demo.ts`. Плашка показывает происхождение текущего расчёта. Страницы «Обзор», «Товары» и «Поставщики» второстепенны; интерактивные настройки поставщиков остаются локальным UI и не меняют расчёт на сервере.

Архив IEK.zip не содержит актуального остатка с датой. Его можно проверить и сохранить, но сервер не выдаст подтверждённый операционный заказ без дополнительной книги текущих остатков. Пример её столбцов: `Код 1С`, `Остаток`, `Дата`, `Склад`. Ошибки качества данных отображаются перед рекомендациями.

## Известные границы контракта

- В согласованной схеме `ImportPreviewResponse` отсутствует `preview_id`, хотя `CommitImportRequest` его требует. Текущий backend добавляет `preview_id` в фактический ответ; контракт должен быть дополнен интегратором после согласования.
- Сервер не передаёт цены, валюту, отдельное утверждение поставщика, историю изменений, закупочную единицу или временной ряд спроса. UI не выводит денежные суммы и не создаёт эти данные. История в серверном заказе не показывается; график остаётся только иллюстрацией на второстепенном экране «Обзор».
- Экспорт CSV/XLSX проверен через API, но формат не объявлен совместимым с конкретной конфигурацией 1С без её образца.
- `frontend/compose.yaml` поднимает только статический frontend. Локальный сценарий выше использует Vite и FastAPI; полноценный общий деплой пока не собран.
